# 饮食记录

一个给自己用的单文件 PWA：拍照记录三餐营养，晨晚双称推导**实测 TDEE** 与热量缺口，追踪体脂与去脂体重。

零依赖、零构建——整个 App 就是一个 `index.html`。

---

## 零、线上地址与首次配置（TL;DR）

**App 地址：https://karachends.github.io/dietlog/** —— 手机、平板、电脑都开这个，加到主屏幕即可。

首次打开要在**每台设备上各做一次**两件事（都只存在该设备的浏览器里，不会写进代码）：

| 要填什么 | 在哪填 | 从哪拿 |
|---|---|---|
| **AI Key**（拍照识别） | 设置 → AI 识图 | 你的 coding plan Key（见下） |
| **同步令牌**（多设备一致） | 设置 → 多设备同步 | 自己建的 Fine-grained PAT（见下） |

两样都不填也能用，只是拍照识别和跨设备同步不可用。

## 二、第一次用要做的三件事

### 1. 填 API Key（拍照识图必需）

**设置 → AI 识图 → API Key**，粘贴你的 DeepSeek Key（`sk-…`）。

- 默认 `deepseek-flash`，走 OpenAI 兼容格式，单图最多约 1024 token，成本极低
- 备选：智谱 `glm-4v-flash`（**完全免费**）、通义 `qwen-vl-plus`
- **Key 只存在这台设备的 localStorage 里**，导出和同步时都会被自动剥离

### 2. 导入你已有的记录

**如果记录散落在某个 AI 会话里**（比如 DeepSeek 聊天记录），直接用
[`导入Prompt-给AI助手.md`](导入Prompt-给AI助手.md)：把里面的 prompt 整段粘贴给那个 AI，
它就会按本 App 的格式导出全部体重与饮食记录，再粘回「设置 → 导入历史记录 → 本地解析」即可。

##### 原始说明：导入你已有的记录

**设置 → 导入历史记录**，把你在 DeepSeek 会话里那段记录**整段粘贴**进去。

格式随意，本地解析器都能认：

```
10月1日 早54.2 晚54.8
早餐 两个鸡蛋 一杯牛奶
午餐 米饭200g 鸡胸肉150g 西兰花

10月2日 早54.0
晚餐 三文鱼150g 米饭150g
```

- **本地解析**：免费、离线、瞬时
- **AI 解析**：更擅长处理格式混乱的文本，需要 Key

解析结果会先给你预览（多少天、多少餐、多少项、多少个体重读数），确认后才写入。

> 好处：**冷启动直接跳过**。不用等两周才有实测 TDEE，导入当天就能算出你真实的热量消耗。

## 三、四个核心功能

### 1. 拍照记饮食

**今日 → 任意餐次 ＋ → 拍照识别**

- 拍摄/选图 → 上传前压到长边 1280 / JPEG 0.82（省流量省 token），原图另存本地缩略图
- 模型返回结构化 JSON（菜名 / 克数 / 做法 / 热量 / 蛋白 / 碳水 / 脂肪 / 钠 / 纤维 / 置信度）
- **每项都会去内置食物库匹配**（267 条中式食物、家常菜、外卖快餐、饮品、调味料），命中就用库里的权威数据，标签显示「库」；没命中保留 AI 估算，标签显示「AI估」
- 改克数**实时重算**全部营养值（内部一律保存每 100g 参考值，按比例换算）
- 支持手动搜索、自定义食物（可按「每份」录入包装食品）、常吃组合一键带出
- 底部「文字快录」：`米饭200 鸡胸150 西兰花100 牛奶250 鸡蛋2个` —— 自动识别 `个/杯/碗/份/勺/片` 等单位换算克数

### 2. 月度体成分档案

**体成分 → 记录本月体成分**

- **上传体脂秤 App 截图，AI 自动读数**（复用同一个视觉接口）
- 记录体重 / 体脂率 / 肌肉量 / 骨骼肌 / 内脏脂肪 / 基础代谢 / 水分率，以及腰臀腿胸臂围度
- **月度变化卡片**：每段区间分别列出体重、脂肪、去脂体重（LBM）的增减
- **结论标签**：`优质减脂`（脂肪降、LBM 守住）/ `肌肉流失` / `脂肪未降`
- **LBM 守卫**：连续区间去脂体重流失 **超过总减重 25%** 时弹告警，并给出蛋白/缺口/力量训练的具体建议
- 有体脂率后，基础代谢自动从 Mifflin-St Jeor 切到 **Katch-McArdle**（更准）

### 3. 每日双称 → 自适应 TDEE（核心）

**今日 → 双称 → 点晨重 / 晚重**

核心恒等式：

```
实测 TDEE = 平均摄入 + 体重下降速率 × 7700
```

- **体重下降速率**用近 **21 天晨重的线性回归斜率**，避开单日水分波动
- **平均摄入**只统计记录完整（≥600 kcal）的天，避免漏记导致低估
- **每日滚动平滑**：`今天 = 0.7 × 上一次 + 0.3 × 实测`，防止一周波动乱跳（幂等，重复计算不漂移）
- 数据不足 7 天时回退公式：有体脂率用 Katch-McArdle，否则 Mifflin-St Jeor × 活动系数
- **达标预测**：按近期实际速率与计划速率的加权，外推「还需 N 天 / 预计 X 月 X 日」

额外挖出来的三个个人化结论：

| 指标 | 含义 |
|---|---|
| **日间涨重** = 晚重 − 晨重 | 正常 0.8~1.5kg。异常高说明当天钠/碳水重，明早晨重会虚高 |
| **晨重 ≈ 晚重 − k** | 用你自己的历史回归出个人系数，睡前称完即可预测明早数字 |
| **钠敏感度** | 每多吃 1g 钠，次日晨重平均变化多少克（附相关系数 r 与样本数 n） |

### 4. 数据总览（日 / 周 / 月 / 年）

全部手写 SVG / Canvas，不引任何图表库。

| 尺度 | 内容 |
|---|---|
| **日** | 环形热量进度（5 条营养素进度条）+ 今日时间线（按时间排序的食物明细） |
| **周** | 日均摄入 / 日均缺口 · 每日缺口柱 vs 目标线 · 宏量堆叠柱 vs 目标线 · 体重散点 + EMA + 回归线 |
| **月** | 同上周 + **月历热力图**（颜色分级：盈余 / 缺口不足 / 接近 / 达标 / 缺口过大） |
| **年** | **365 天贡献热力图**（GitHub 风格，可左右滑动）+ 全年体重曲线 + 月度汇总表 |

热力图任意格子可点击，直接跳到那天。

这些不是摆设，是会在首页顶部真实弹出的：

| 护栏 | 触发条件 |
|---|---|
| ⚠️ 目标速率超区间 | 每周速率 > 体重的 1.0% |

## 八·五、交互缺陷修复记录

### 轮次 2：桌面端面板完全无法交互（严重）

**现象**：在宽屏电脑上，弹出录入面板后**所有按钮都点不动**，面板也关不掉，看起来像两个面板半透明叠在一起。

**根因**：`.sheet` 的关闭态只靠 `transform` 位移，而桌面媒体查询里的位移量是**面板自身高度的 102%**：

```css
/* 错误写法 */
@media(min-width:760px){
  .sheet{top:50%; margin-top:-320px; transform:translate(-50%,102%)}
}
```

`102%` 是相对**自身高度**的，不是相对视口。桌面上面板基准位置是 `top:50% - 320px`（约在屏幕中上部），
往下挪 `1.02 × 自身高度` 根本清不出 `100vh`。实测残留量：

| 视口 | 已关闭面板残留在视口内的像素 |
|---|---|
| 390×844（手机） | **0px** ✅（`bottom:0` + `translateY(102%)` 能清干净，所以手机一直正常） |
| 1536×960 | 69 ~ 291px ❌ |
| 1271×1270 | 59 ~ **446px** ❌ 将近半屏 |

而残留的关闭面板 `pointer-events:auto`、`visibility:visible`，且在 DOM 里排在打开的面板**之后**，
于是盖在上层把点击全部吞掉——`elementFromPoint` 显示「关闭」按钮的位置上实际是另一个面板的 `textarea`。

**修复**（三件事同时做，缺一不可）：

```css
/* 1. 关闭态：移出视口 + 不可见 + 不吃点击 */
.sheet{transform:translateY(102%); opacity:0; visibility:hidden; pointer-events:none;
  transition:transform .3s cubic-bezier(.32,.72,0,1), opacity .2s ease, visibility .3s}
.sheet.on{transform:translateY(0); opacity:1; visibility:visible; pointer-events:auto}

/* 2. 桌面态：位移量改用 100vh，保证无论多高都能完全移出；打开态真正居中 */
@media(min-width:760px){
  .sheet{top:50%; left:50%; right:auto; max-height:88vh; max-height:88dvh;
    transform:translate(-50%, calc(-50% + 100vh))}
  .sheet.on{transform:translate(-50%,-50%)}   /* 不再依赖写死的 margin-top:-320px */
}
```

3. 补 `.sheet{overflow:hidden}` 与 `.sheet-in{flex:1 1 auto; max-height:100%}`，保证内容再多也是
   内部滚动、底部按钮永远留在视口内。
4. 新增 **Esc 键关闭**面板，作为桌面端永远可用的兜底退出方式。

| # | 缺陷 | 根因 | 影响 | 修复 |
|---|---|---|---|---|
| 1 | **体重精度被抹掉**：`55.05` 存成 `55.1`、`53.65` 存成 `53.7` | 全链路用 `r1()` 只保留 1 位小数 | 用户记的是「斤」（106.5斤 = 53.25kg），2 位精度是真实数据，抹掉后 21 天回归斜率会失真 | 新增 `r2()` 用于存储；新增 `fw()` 自适应显示（整数 1 位、有小数 2 位，避免用户以为没存进去） |
| 2 | **食物匹配严重错配**：`烧鸡` 匹配到 `板烧鸡腿堡` | `contains` 规则只判断子串包含就给 0.85 置信度。`烧鸡` 恰好是 `板烧鸡腿堡` 的子串 | **150g 算出 645 kcal，真实约 285 kcal**，静默污染热量统计 | 加长度比闸门（`min/max ≥ 0.6`），置信度改为 `0.6 + 0.3×ratio`，阈值提到 0.7；Dice 阈值 0.45→0.55 |
| 3 | **常见食物缺失导致 0 热量**：`芝士`、`牛肉丸`、`烧鸡`、`卤猪蹄`、`炒青菜` 等 | 食物库只有 267 条，覆盖不全 | 未匹配项热量记 0，当天摄入被低估 | 补到 **278 条**；并把未匹配项标成红色 **待补** 徽章，便于逐个修正 |
| 4 | **导入器不支持状态备注与体成分** | 只解析日期/体重/餐次 | 状态信息（练背/抽血/生理期）丢失，而这些正是体重波动的解释变量 | 新增 `备注 xxx` 行与 `体成分 日期 体重… 体脂率…` 行；备注在今日页以可编辑 chip 显示 |

顺带把 `火腿` 的匹配优先级调成「火腿片」优先于「火腿肠」（早餐语境里更合理）。

**教训**：`烧鸡 → 板烧鸡腿堡` 这类错配不会报错、不会崩溃，只会安静地把 645 kcal 记进你的账本。
所以模糊匹配必须有长度闸门，并且**未匹配项要显式暴露给用户**，而不是悄悄记 0。

### 轮次 4：AI 导出把解释文字混进数据区 → 散文变成「食物」

**现象**：导入后今日页出现了这样的「食物」：

| 食物 | 量 | kcal |
|---|---|---|
| 红薯130g。推导依据：出现在"昨晚练了核心和 | 100g | 0 |
| 今天 | 100g | 0 |
| 这个" | 100g | 0 |
| 但无法确定具体日期。 | 100g | 0 |

**根因有两层**：

1. **上游**：那个 AI 没遵守 prompt，把「日期存疑」的解释文字写进了数据区。
2. **下游（我的责任）**：解析器对输入零防御——**任何不认识的句子都当成食物**，兜底给 100g / 0 kcal。

**修复**：

| 措施 | 说明 |
|---|---|
| `cleanDataLine()` | 在句末标点 / 引号 / 非数值冒号处截断，**砍掉解释文字但保住前面的真实数据**。`红薯130g。推导依据：出现在…` → 救回 `红薯130g` |
| `isFoodName()` | 校验候选名：长度 > 12 字、含句子标点、含说明性词汇（无法/确定/依据/推导/日期/存疑…）的一律拒绝 |
| 独立相对词不当日期锚 | `今天` 单独成行是散文碎片。若认作日期，**后面的真实食物会被整体挪到错误日期** |
| 提交时二次过滤 | `commitImport` 再挡一次，脏条目根本不入库 |
| **🧹 一键清洗** | 设置 → 数据 → 「清洗导入的脏数据」，扫描已入库数据、删掉不像食物的条目，并**列出被删清单供核对**（避免误删） |

**关键的设计取舍**：散文词表用「**包含即判**」而不是「开头才判」——否则 `但无法确定具体日期` 因为开头是「但」而非「但是」就会漏过去。
代价是理论上有误杀风险，所以我做了双向验证：**278 条食物库名称零误杀**，17 类散文碎块全部挡住。

**同时把 prompt 加固**：新增「绝对不要做的事」章节，给出正反例，明确要求食物名 ≤8 字、一行 ≤6 项、任何一行不得出现标点。

**教训**：解析用户或 AI 生成的自由文本时，**兜底策略必须是「拒绝」而不是「接受」**。
我原来的兜底是「认不出来就当 100g 食物」，等于把噪声直接写进用户的账本。
正确做法是「认不出来就不收，并让用户看见」——这和食物匹配那条「未匹配项要显式暴露」是同一个原则。

### 轮次 5：食物名可编辑 + 自动补全成分 + 手动调整

**需求**：已经录入的饮食要能改食物名，改完系统自动补全营养成分，同时也允许手动填写。

**实现**：

| 能力 | 说明 |
|---|---|
| **食物名直接可编辑** | 录入面板里每项的食物名从纯文本改成输入框，改完（失焦或回车）自动去食物库查成分 |
| **自动补全** | 命中就套用库里的每 100g 数据，按当前克数立刻重算；徽章从红色「待补」变绿色「库」 |
| **匹配透明化** | 若输入名与库条目不同（如输入「鸡胸」→ 实际用「鸡胸肉(生)」），条目下方明确写出**实际采用了哪条**，避免被悄悄换成别的东西 |
| **没命中不瞎猜** | 保持「待补」状态并提示可手动填，不会塞一个错误的默认值 |
| **手动调整** | 每项有「手动调整」按钮，展开后可直填热量/蛋白/碳水/脂肪/钠；点应用后**反推每 100g 基准**，所以之后改克数仍会自动按比例重算 |
| **克数逻辑不受影响** | 三条路径（库匹配 / AI 估算 / 手动填写）统一走同一个 `ref` 每-100g 基准 |

**同时补掉上一轮清洗的漏网**：`===`、`核对清单`、`【核对清单】` 这类碎块。
`核对清单` 是 4 个汉字，通过了长度和字母校验，所以必须另外处理：
- 散文词表补充 `清单|核对|统计|汇总|合计|总计|小计|分隔|标题`
- 新增「去安全标点后必须主要是文字数字」的校验，纯符号串（`===`、`***`、`——`）直接拒绝

**又一次双向验证**：**278 条食物库名称零误杀**，24 类散文/符号碎块全部挡住。

**一个实现细节的坑**：改名处理最初被我挂在了 `input` 事件上，结果每次按键都重渲染、输入框直接失焦。
正确做法是挂 `change`（失焦或回车才触发）。这个 bug 是自动化测试发现的——断言「真实输入框改名」时没生效。

### 教训

轮次 1 的测试**只在 390×844 手机视口跑**，完全没覆盖 `@media(min-width:760px)` 那条桌面分支——
而用户正是在桌面上用的。修复后新增了**跨 5 个视口**的验收（含 1271×1270 用户实际比例）。

另外一个坑：**`.click()` 会绕过浏览器命中检测**，被遮挡的元素它照样触发。
必须用 CDP 派发真实坐标鼠标事件 + `document.elementFromPoint` 做遮挡检测，
才测得出「按钮看得见但点不到」这类问题。

### 8.3 跨视口验收（85 项断言，全部通过）

同一套真实点击测试在 **5 个视口**下各跑一遍：

| 视口 | 说明 |
|---|---|
| 390×844 | iPhone 竖屏 |
| 768×1024 | iPad 竖屏（刚好越过 760px 桌面断点） |

## 十、多设备同步

### 它是怎么工作的

没有后端、没有账号：靠一个**私有的 GitHub 仓库** `KaraChenDS/dietlog-data` 当文件中转，
里面只有一个 `dietlog.json`。每台设备各自推送/拉取，客户端负责合并。

```
手机 ──npm──▶  dietlog-data/dietlog.json  ◀──── 电脑
        ▲                                  ▲
        └──────── 平板 ────────────────────┘
```

### 自动到什么程度

| 时机 | 动作 |
|---|---|
| 打开 App | 静默拉取并合并 |
| 任何改动后 | 防抖 2.5 秒静默推送 |
| 切回前台 | 再拉一次（手机刚记的，电脑切回来就有） |
| 网络恢复 | 再拉一次 |
| 云端还没有文件 | 用本机数据自动创建（首次引导） |

首页顶部有一条状态：`☁️ 已同步 · 2 分钟前`，点它可立即刷新。失败会变红并写明原因。

### 每台设备的令牌

代码里**只有仓库地址，没有任何令牌**。每台设备自己贴一个 Fine-grained PAT：

1. 打开 https://github.com/settings/personal-access-tokens/new
2. **Repository access** → Only select repositories → 只勾 **`dietlog-data`**
3. **Permissions → Repository permissions → Contents** → **Read and write**（其余不动）
4. 生成后复制，粘到 App 的 **设置 → 多设备同步 → 本机同步令牌**

> 为什么每台设备一个：静态页面无法安全持有密钥。令牌只落在该设备的 localStorage，
> 导出 JSON 和同步载荷都会**主动剥离**它（有自动化断言守着这条）。

**想省事**：在已连好的设备上点「🔗 一键连接链接」，把链接发到新设备浏览器打开即可自动连上。
链接含令牌，会留在聊天记录里，用完建议去 GitHub 作废重建。

### 合并规则（这是最容易做错的地方）

不是「整条记录取较新」，而是**按字段分层合并**：

| 数据 | 规则 |
|---|---|
| 每天的**晨重/晚重/备注** | 各自带时间戳，逐字段取较新的一侧 |
| 每天的**每一餐** | 按餐次各自合并 —— 手机记早餐、电脑记晚餐，两边都保住 |
| **删除** | 用「置空 + 更新时间戳」表达，所以删除也能跨设备生效，不会被旧版本复活 |
| **体成分** | 按日期唯一（一个月一条），取时间戳较新 |
| **目标/速率等设置** | 整体按 `settingsTs` 取较新 |
| **常吃组合 / 自定义食物** | 按名字并集 |

另外：**拉取后会判断「本机是否比云端更全」并回写**。
没有这一步，一台设备在「连接之前」就已有的本地数据永远上不去，表现就是「手机记了，电脑看不到」。

### 同步什么、不同步什么

| 同步 | 不同步（留在本机） |
|---|---|
| 饮食、体重、体成分、备注 | 照片 |
| 目标体重/速率/宏量设置 | AI Key |
| 常吃组合、自定义食物 | 同步令牌 |
| | TDEE 计算缓存 |

## 十一、AI 识图走 coding plan

### 密钥从哪来

你的 coding plan API Key 定义在 **`~/.zshrc` 第 3 行**（一个全局环境变量 `CODING_PLAN_API_KEY`），
所以 DSH 和其它 GUI 应用都能读到它。把那个值复制出来，粘到 App 的「设置 → AI 识图」。

> 注意：要粘**密钥本身**（约 33 字符）。填错会得到 HTTP 403 —— App 会明确提示「密钥被拒绝」，
> 而不是含糊地说解析失败。

### 这个网关有三个坑（都已实测并处理）

| 坑 | 现象 | App 的处理 |
|---|---|---|
| **默认强制 SSE 流** | 不带 `stream` 字段时返回 `text/event-stream`，`res.json()` 直接解析失败 | 请求显式带 `"stream": false`；另外保留 SSE 解析兜底，网关万一忽略该字段也能拼回正文 |
| **推理模型很吃 token** | `deepseek/deepseek-v4.1-flash` 识别一餐要用 **5126** 个 token（几乎全花在思考上），`max_tokens` 给小了正文为空 | 上限提到 **8000**；正文为空且只有 `reasoning_content` 时给出明确提示 |
| **鉴权失败返回 403 而非 401** | 缺失鉴权头才是 401，错误的 Bearer 一律 403 `forbidden` | 把 401/403 都映射为「密钥被拒绝」，并说明要填的是 Key 本身 |

### 模型实测对比

同一张食谱图 + 真实识别 prompt，5 个支持图片的模型表现：

| 模型 | 耗时 | 输出 token | 识别结果 |
|---|---|---|---|
| **`zhipu/glm-5.3-flashx`** | **6s** | **729** | 白米饭 / 煎牛排 / 西兰花 ✅ **默认** |
| `ali/qwen3.8-flash` | 28s | 2170 | 白米饭 / 煎猪排 / 西兰花 |
| `deepseek/deepseek-v4.1-flash` | 27s | 5126 | 白米饭 / 煎猪排 / 豌豆 |
| `xiaomi/mimo-v2.6-pro` | 43s | 1830 | 白米饭 / 煎鸡排 / 西兰花 |
| `deepseek/deepseek-v4-pro` | 7s | 246 | **0 项** ❌ 不推荐 |

所以默认选了 **`glm-5.3-flashx`**：比 v4.1-flash 快 4.5 倍、省 7 倍 token，识别还更准。
设置页可以一键切换其它模型。

### CORS

已实测该端点返回 CORS 头（`access-control-allow-origin` 回显请求来源、
`access-control-allow-methods: POST`），所以静态页面可以直连，**不需要任何代理**。

## 十三、同步功能的验证方式

用 **Chrome headless + CDP** 驱动真实浏览器，**物理隔离**真实数据：

1. 为测试单独建了 `dietlog-testdata` 仓库，测试**永远**指向它；
2. **在应用加载之前**注入测试配置 —— 应用加载后约 700ms 会自己拉一次，
   如果那时配置还指着真实仓库就已经写进去了；
3. 每次运行用**随机文件名**，避免上一轮残留影响；
4. 令牌从环境变量 `SYNC_TOKEN` 传入，**不写进脚本**；
5. **请求审计**：监听 `Network.requestWillBeSent`，列出所有打向 `api.github.com` 的请求，
   出现写真实仓库的 PUT 就报错。

一轮完整测试后确认真实数据仓库**仍是空的**（用 API 校验）。

必测场景全部覆盖：404 首次引导、令牌不进载荷、跨设备拉回、分层合并不丢数据、
删除墓碑、内容未变不误报、401 优雅处理、诊断输出、防抖自动推送、
真实仓库零写入、测试文件清理。
